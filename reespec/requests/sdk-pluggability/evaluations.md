### typed-events
verdict:  ❌ UNSATISFIED
reason:   CRITICAL GAP: The event types are pi mirrors, not reeboot abstractions. Every event has identical field names and shapes to pi — only type references differ (`AgentMessage` → `unknown`, `ToolResultMessage[]` → `unknown[]`). BeforeAgentStartEvent: identical `{type, prompt, images?, systemPrompt, systemPromptOptions}`. TurnEndEvent: identical `{type, turnIndex, message, toolResults}`. ToolCallEvent: identical discriminated union with `toolName` + `input`. SessionShutdownEvent: identical reason union. The adapter's `transformEvent` is `return piEvent as ExtensionEventMap[K]` — a no-op cast with zero transformation. This means: (1) if pi changes an event shape, reeboot breaks at runtime, (2) if reeboot renames `turnIndex` → `turnId`, pi breaks, (3) a future SDK adapter cannot just cast — it would need transformation logic, but there is no reeboot-defined shape to transform to/from. The `ExtensionContext` proves this can be done differently: it has a completely independent shape and the adapter genuinely maps between them. The events should follow the same pattern — reeboot defines its own shapes, the adapter transforms pi → reeboot, and a future SDK adapter transforms SDK → reeboot. The spec S1-S7 requirements are technically met (fields exist, types exported, discriminants present) but miss the architectural intent: events must be SDK-agnostic so multiple SDKs can plug in without extensions knowing which SDK is active. S5 TurnEndEvent spec described `turnId, sessionId, usage` — this was actually the right instinct. `turnId: string` is more SDK-agnostic than pi's `turnIndex: number` (not all SDKs use numeric indices). The spec was wrong about pi's actual shapes but right about the design direction.

### pi-adapter

reason:   S1 (implements ExtensionAPI ✓), S2 (registerTool forwards to pi ✓), S3 (on() maps events to pi ✓), S5 (setSessionName forwards ✓), S6 (getSessionName retrieves ✓), S7 (sendMessage forwards ✓), S8 (context provided ✓) are satisfied. S4: on() returns `() => void` no-op — this is correct because pi's on() returns `void` (no unsubscribe), not a gap. S9: transformEvent is a bare `return piEvent as ExtensionEventMap[K]` pass-through — this works because reeboot's event field names match pi's exactly (turnIndex, toolCallId, input, etc.), but if reeboot ever diverges (e.g., renames turnIndex→turnId), the adapter won't transform. This is a latent gap for future SDK adapters. S10: `new PiExtensionAdapter(null, context)` succeeds (✓), but `registerTool()` on null session throws `TypeError: Cannot read properties of null (reading 'registerTool')` — not a descriptive error as spec requires. Also: ToolResultEvent in reeboot is missing pi's `input: Record<string, unknown>` field from the base type — the pass-through cast means it exists at runtime but extensions can't access it through the typed interface.
focus:    pi-adapter.ts — null-session error quality (S10), ToolResultEvent missing `input` field, transformEvent is pass-through (latent gap for future SDK adapters)
